静态站点生成器的构建时间通常不是问题，直到文章数量上了三位数。
每次全量重建会让「保存即预览」变得难以忍受。

## 判断"变了没有"

最省事的做法是给每个源文件算一个哈希，存进缓存文件：

```js
const hash = createHash('sha1')
  .update(`${raw}\u0000${postLayout}`)
  .digest('hex')
  .slice(0, 16);
```

两个细节值得说明。

**哈希里带上布局。** 如果只哈希原文，改一次模板就要手动清缓存 —— 这是最容易
忘的一步。把布局内容一起算进去，改模板自然会让所有页面失效，行为符合直觉。

**缓存放在输出目录。** `dist/.marklite-cache.json`。删掉输出目录等于清空缓存，
不会出现"缓存说没变但产物已经被删了"的情况。为了保险，命中缓存前还会检查
产物文件是否真的存在。

## 缓存结构

| 字段 | 用途 |
| --- | --- |
| `hash` | 原文 + 布局的指纹 |
| `out` | 输出文件名 |

只有两项。缓存里存更多信息（比如依赖了哪些 include）会让它更像一个构建系统，
但也更容易和现实脱节 —— 一旦缓存和文件状态不一致，排查成本远高于省下的几毫秒。

## 清理孤儿页面

文章改名或删除后，`dist/` 里会留下没人访问的旧文件。构建末尾扫一遍输出目录，
把不在预期集合里的 `.html` 删掉：

```js
const expected = new Set(['index.html', ...posts.map(p => `${p.slug}.html`)]);
for (const file of produced) {
  if (!file.endsWith('.html') || expected.has(file)) continue;
  await fs.unlink(path.join(outDir, file));
}
```

这一步只在本地开发时有风险（删错文件），所以刻意只处理 `.html`，其他静态资源
一概不碰。

## 效果

二十篇中等长度的文章，全量构建约 60 毫秒，改一篇后重建约 8 毫秒。
在开发服务器的轮询周期（800 毫秒）面前，这个差异其实感知不到 ——
但文章涨到两百篇时，它决定了你还愿不愿意开着预览窗口写。
